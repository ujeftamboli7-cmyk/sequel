SQL Assignment 6: Transactions and Triggers

Question: Create a SQL script to insert a new order into an Orders table, then use COMMIT to save the transaction and verify that the new order persists after reconnecting to the database.

Answer:

-- Insert a new order
INSERT INTO Orders (order_id, user_id, order_total)
VALUES (101, 1, 1500);

-- Save the transaction
COMMIT;

-- Verify the inserted order
SELECT *
FROM Orders
WHERE order_id = 101;


Explanation:

INSERT INTO adds a new order to the Orders table.
COMMIT permanently saves the transaction.
SELECT verifies that the order exists.
After reconnecting to the same database, run the SELECT query again to confirm that the order persists.

Assumption: The Orders table contains the columns order_id, user_id, and order_total.


Question: Simulate a Zomato-style food order process by inserting two new items into an OrderItems table, then use ROLLBACK to undo the changes before committing. Verify that no new items remain after rollback.

Answer:

-- Insert the first food item
INSERT INTO OrderItems (item_id, item_name, quantity)
VALUES (201, 'Pizza', 1);

-- Insert the second food item
INSERT INTO OrderItems (item_id, item_name, quantity)
VALUES (202, 'Burger', 2);

-- Undo both insertions
ROLLBACK;

-- Verify the changes were undone
SELECT *
FROM OrderItems
WHERE item_id IN (201, 202);


Explanation:

Two food items are inserted into the table.
ROLLBACK undoes both insertions because they have not been committed.
The final query should return no rows for these newly inserted items, assuming those IDs did not already exist.

Note: Do not execute COMMIT before ROLLBACK, because committed changes cannot be undone using a normal transaction rollback.

Question: In a Flipkart-like shopping cart scenario, use SAVEPOINT after adding a product to the Cart table. Add another product, then use ROLLBACK TO SAVEPOINT to undo only the last addition. Display the final contents of the cart.

Answer:

-- Add the first product
INSERT INTO Cart (cart_item_id, user_id, product_name)
VALUES (301, 1, 'Headphones');

-- Create a savepoint
SAVEPOINT product_added;

-- Add the second product
INSERT INTO Cart (cart_item_id, user_id, product_name)
VALUES (302, 1, 'Smart Watch');

-- Undo only the second insertion
ROLLBACK TO product_added;

-- Display the final cart contents
SELECT *
FROM Cart
WHERE user_id = 1;

-- Save the remaining changes if desired
COMMIT;


Explanation:

The first product, Headphones, is inserted.
SAVEPOINT product_added marks the transaction state after the first insertion.
The second product, Smart Watch, is inserted after the savepoint.
ROLLBACK TO product_added undoes the second insertion but preserves the first.
COMMIT saves the remaining transaction.

Expected result: The cart contains Headphones, while Smart Watch is removed by the rollback.

Question: Write a trigger on a Wallet table that automatically deducts the purchase amount from the user's balance whenever a new transaction is inserted, similar to how Paytm updates wallet balance after a payment.

Answer:

Assumption: The Wallet table contains user_id and balance. The WalletTransactions table contains transaction_id, user_id, and amount. This example uses Oracle PL/SQL.

CREATE OR REPLACE TRIGGER deduct_wallet_balance
AFTER INSERT ON WalletTransactions
FOR EACH ROW
BEGIN
    UPDATE Wallet
    SET balance = balance - :NEW.amount
    WHERE user_id = :NEW.user_id;
END;
/


Example transaction:

INSERT INTO Wallet (user_id, balance)
VALUES (1, 5000);

INSERT INTO WalletTransactions
    (transaction_id, user_id, amount)
VALUES
    (401, 1, 1000);

SELECT user_id, balance
FROM Wallet
WHERE user_id = 1;


Expected output:

user_id	balance
1	4000

Explanation:

AFTER INSERT runs the trigger after a transaction is inserted.
FOR EACH ROW executes it for every inserted transaction.
:NEW.amount represents the newly inserted purchase amount.
The trigger deducts that amount from the matching user's wallet balance.

Important: This basic trigger assumes sufficient funds and an existing wallet. A production wallet system should also validate balances, handle concurrent transactions safely, and reject invalid or negative purchase amounts.

Question 5: Identify and Fix a Bug in a Wallet Trigger

Question: Generate a SQL test scenario where a trigger incorrectly updates a user's balance after an expense entry. Provide the scenario, corrected trigger code, and explain how the error was fixed.

Answer:

A. Buggy Trigger

The following trigger incorrectly adds the expense amount to the wallet balance instead of deducting it.

CREATE OR REPLACE TRIGGER update_wallet_bug
AFTER INSERT ON WalletTransactions
FOR EACH ROW
BEGIN
    UPDATE Wallet
    SET balance = balance + :NEW.amount
    WHERE user_id = :NEW.user_id;
END;
/

B. Test Scenario

Assume the user's wallet balance is ₹5,000 and a purchase of ₹1,000 is made.

INSERT INTO Wallet (user_id, balance)
VALUES (2, 5000);

INSERT INTO WalletTransactions
    (transaction_id, user_id, amount)
VALUES
    (501, 2, 1000);

SELECT user_id, balance
FROM Wallet
WHERE user_id = 2;


Incorrect output:

user_id	balance
2	6000

Problem: The trigger adds ₹1,000 instead of deducting it. The correct balance should be ₹4,000.

C. Corrected Trigger
CREATE OR REPLACE TRIGGER update_wallet_correct
AFTER INSERT ON WalletTransactions
FOR EACH ROW
BEGIN
    UPDATE Wallet
    SET balance = balance - :NEW.amount
    WHERE user_id = :NEW.user_id;
END;
/

D. Verify the Fix

For a clean test, reset the test wallet balance to ₹5,000 and use a new transaction ID.

UPDATE Wallet
SET balance = 5000
WHERE user_id = 2;

INSERT INTO WalletTransactions
    (transaction_id, user_id, amount)
VALUES
    (502, 2, 1000);

SELECT user_id, balance
FROM Wallet
WHERE user_id = 2;


Expected output:

user_id	balance
2	4000
E. Explanation of the Fix
Bug: The original trigger used balance + :NEW.amount, increasing the balance after an expense.
Correction: The fixed trigger uses balance - :NEW.amount, deducting the expense from the balance.
Verification: With an initial balance of ₹5,000 and an expense of ₹1,000, the final balance is ₹4,000.

Testing note: Run the buggy and corrected trigger tests separately. If the corrected trigger is already installed, creating a new transaction will execute that trigger rather than the buggy one.
